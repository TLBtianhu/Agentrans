# apps/web 浏览器 e2e

[English](README.md) | 中文

这些测试在进程内启动真实的 web 组合，并用真实浏览器通过真实 HTTP 驱动它。Chromium 运行整个 lane；[模型与推理强度选择场景](declared-reasoning.e2e.ts) 还在 WebKit 中运行，以覆盖原生鼠标焦点行为。[会话回放恢复](session-replay-reload.e2e.ts)还在 WebKit 中运行，共用 `fresh-round-trip` 的录制和预期输出，不改写这些文件。该用例覆盖输出中刷新、完成后刷新和重新打开 Session。该 lane 的运行机制——模式、fixture（测试前置数据）、golden，以及与 `agentrans web` 之间刻意保留的组合差异——记录在 [`scaffold.ts`](scaffold.ts) 和 [浏览器 e2e Agent Note](../../../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.zh.md) 中。

安装工作区依赖后，在仓库根目录安装浏览器及其系统依赖：

```sh
pnpm --filter @agentrans/web-frontend exec playwright install --with-deps chromium webkit
```

在 Linux 上，`--with-deps` 会通过系统包管理器安装依赖。持久化 CI VM 必须通过镜像维护提供这些依赖，CI 只安装浏览器程序，遵循[故障切换手册](../../../.agents/notes/implemented/process/2026-07-26-ci-failover-runbook.zh.md)的要求。

普通场景以没有已登记 Workspace 或 Session、但持久化标记记录默认 Workspace 已被删除的状态启动，使显式文件夹选择场景自行决定 cwd。`launchWebScaffold({ firstUse: true })` 保留初始化资格，供启动场景使用。

当天消息的 golden 使用共享的 `WEB_FIXTURE_TIME`：预置会话将它传为 `createdAt`，并通过 `pinBrowserClock` 固定浏览器日期；提交实时消息的场景还使用 `pinHostClock`，在清理后恢复。固定后的时钟随真实耗时前进，保留原生定时器，因此跨午夜不会改变场景的日期标签。

## Fixture 归属

`snapshots/web/` 拥有同时用作回放输入和完整持久化预期输出的已记录 Session。其 `snapshot.yml` 声明组合、录制和 header 归属。浏览器用例可以借用既有 corpus owner；即使 `compareReplaySession` 为 `false`，scaffold 也会在启动前校验该 owner。

`fixtures/replay/` 拥有仅作输入的 Session 格式回放脚本。这些用例显式设置 `compareReplaySession: false`，通过 `assertFixtureInventory` 检查 fixture 角色与规范化，并断言真实浏览器和 Host 行为。这些断言不使输入成为完整持久化或迁移 oracle。父子文件须保持成组。经审阅的位置调整保持文件字节和 generation 名称，不录制或刷新 Session。参见 [corpus 规则](../../../snapshots/AGENTS.md)。

## 真实 Artifact 验收

真实 Artifact 验收要求非空的 `DEEPSEEK_API_KEY`、`AGENTRANS_ARTIFACT_LIVE=1` 和 `AGENTRANS_SNAPSHOT=record`。将 `AGENTRANS_ARTIFACT_LIVE_OUTPUT_DIR` 设置为证据目录后，运行 `node node_modules/vitest/vitest.mjs run --config vitest.web.config.ts apps/web/tests/artifact-live.e2e.ts --maxWorkers=1 --retry=0 --reporter=verbose`。设置 `AGENTRANS_PLAYWRIGHT_EXECUTABLE_PATH` 可使用已有的 Chromium 兼容浏览器。每个用例在独立工作区使用随附的 `deepseek-flash` 模型。验收检查默认 Agent 在需要动手验证时是否主动提供函数图和粒子实验、能否按确认的读数更新同一个 Artifact，以及能否直接回答简短的求导问题。分支用例验证模型提供商收到带有所选回流读数的普通追问，并在刷新后从该追问复现。粒子续做用例仅调整回流采样点的竖直重力，将确认的读数交给模型追问，并在刷新后复现前后两次回流的读数。生成式广度优先搜索用例验证，模型收到分支内确认的检查点，主对话从采纳的步进器确认新读数并追问，刷新后两份检查点可分别恢复。生成式半加器用例检查全部四组真值表，分别为分支和主对话的追问锁定两组输入输出，并在刷新后独立恢复。每个证据目录保存 Session、截图和 HTTP 请求状态。[真实验收用例](artifact-live.e2e.ts)

双缝干涉用例在全新工作区请求一个实验，检查模型是否加载随产品分发的设计技能并使用参数探索模板。它还验证缝距调整、拖动探针，以及 390 像素视口中键盘操作后的光程差。

BFS 和半加器的 Web 回放先锁定读数并回流，再回原分支更新同一个 Artifact 的样式。刷新主对话后，浏览器从原回流卡下载，并离线核对原修订、锁定读数和原样式。BFS 能走到 C、D 并重置到 B。半加器能遍历四组真值并重置为两个输入都开启。下载期间不调用模型、不创建分支、不写入会话事件。[无密钥回放](artifact-program-question.e2e.ts)

对话预设的 CSV 用例上传测量数据，检查模型是否用附件 ID 和聚合条件请求原生柱状图，然后锁定 Warm 的均值并切到 Cold。它验证模型收到这条均值读数、同一个 Artifact 显示新的总和，以及主对话刷新后仍能复现均值。从历史下载的 HTML 可离线打开，显示原修订的各组数据。

CSV 继续分析用例把 Warm 的均值带回主对话。切换到总和后，锁定 Warm 的两行数据合计 60，再选择总和为 100 的 Cold。用例确认对照和锁定不会调用模型，追问发出的是锁定的 Warm 总和。刷新后，已发送的追问可对照回流均值 30 和锁定总和 60，并显示两条 CSV 记录均保留。

CSV 筛选用例选择 `Batch = B`，对照筛选前 Warm 两条记录的总和 60 与筛选后一条记录的总和 35。用例核对参与记录的原始序号和单元格，然后锁定读数并切换到 Cold。发送追问时，模型提供商收到锁定的 Warm 读数和确切筛选条件。刷新后，回流均值 30 可展开第 4、5 条记录，已发送追问的筛选总和 35 可展开第 5 条记录。追问中的对照同时显示两份读数，并标明第 4 条被排除、第 5 条保留。用例在 390 像素宽的视口检查表格，并验证每次查询均无模型调用，且不写入主对话或分支。无密钥用例验证源记录不可用时，两张卡片均保留历史读数，三处查询均可重试。

同一真实用例核对并附上筛选后的对照、输入解释问题，检查 Edge 刷新后仍能恢复未发送文字和已核对记录。随后停掉 Web 宿主，在同一 Vitest 进程内用原测试数据目录和原站点地址启动新的宿主运行时和 HTTP 监听器。重新认证后，Edge 再次恢复草稿。用例打开另一条已发送追问的无筛选对照，直接发送恢复的文字。模型提供商收到原样核对过的事实，附件校验证明和草稿回执留在宿主处理环节。模型根据第 4、5 条记录解释原均值 30、无筛选总和 60 和筛选后的总和 35。发送被接收后，宿主清除草稿。刷新后，解释追问从已保存的消息复现相同的附带对照，无须重算或调用模型。

用例三次主动关闭 Edge 标签页以验证发送恢复。第一次在宿主绑定草稿回执后拦截追问，关闭标签页前未将追问交给宿主，重开后恢复原文字和对照，且不会自动发送。后两次在宿主登记已绑定请求 ID 后暂停接收。等待确认时，输入仍可编辑，参与行可核对，发送按钮禁用，点击或按 Enter 均不会发出请求。宿主拒绝接收时，当前页面提示宿主尚未收到上一条追问，重新启用发送，并保留编辑后的文字和锁定的对照。最后一次接收原请求后，输入框提示已发送，移除已发送的附件，并保留下一条追问的文字。点击 **查看已发送的追问** 会定位到原消息，展开对照并移动焦点。用键盘激活 **返回草稿** 会回到输入框并恢复原光标位置。刷新后从历史复现仍能看到原附件。用例验证上述操作没有重发追问、重新计算对照或额外调用模型。

CSV 筛选用例还从原追问复用对照。取消核对会保留原草稿。确认后，宿主核对确切的历史消息，并把同一份读数和参与行附到草稿。只有手动发送新追问才调用模型。从草稿或已发送的对照中点击 **查看这次复用的来源追问** 会打开那条追问保存的对照。浏览器从草稿沿来源往前两层，在最早的对照处刷新，验证逐级返回和从 **来源路径** 直接跳回中间对照或原草稿，核对原光标位置和附件凭据。返回后再次刷新，路径保持关闭。导航时不读取原 CSV、不重算或调用模型。

CSV 两步解释用例逆序选中同一次分支回流的两份已保存对照。确认后的附件先展示第 4、5 条记录参与的 Warm 均值 30 和总和 60，再展示 `Batch = B` 排除第 4 条、保留第 5 条后的总和 35。发送前，浏览器从同一草稿分别打开两个来源，在各自来源页刷新，再返回原问题、编辑器选区和已确认附件。用例随后核对 DeepSeek 收到的附件及两步解释，并在已发送的追问刷新后分别打开两份原始对照。全程不读取原 CSV、不重算，用户手动发送时只调用一次模型。

无密钥回放从同一条两步解释分别打开两个已保存的来源。刷新来源页后，点击 **返回两步解释** 会展开原解释，将焦点移回对应步骤的来源按钮。再刷新时，已结束的来源路径保持关闭。用例确认全程没有模型调用、附件读取或 CSV 重算。[无密钥回放](csv-comparison-explanation-replay.e2e.ts)

无密钥草稿用例从附到未发送追问的两步解释分别打开两个已保存的来源。刷新来源页后，点击 **返回草稿** 会恢复原问题、编辑器里的精确选区和两份锁定页。再刷新时，已结束的来源路径保持关闭，草稿仍在。用例确认全程不发送追问、不调用模型、不读取附件或重算 CSV。

无密钥导出用例将已发送的两步解释下载成一个 HTML。关闭宿主后，浏览器离线打开本地文件，核对两步读数，并分别展开原始锁定页核对保存的参与行。用例确认全程不调用模型、不读取原 CSV、不重算。[CSV 离线导出](csv-sent-comparison-export.e2e.ts)

两步解释的便携用例将确切的两页下载为带版本的 JSON，再导入全新对话。Edge 在标有 **用户导入** 的预览和历史复现中分别打开原始页。手动发送一次后，DeepSeek 收到这两份确切的页面和导入标记。用例确认全程不读取原 CSV、不重算，也无其他模型调用。[真实两步导入导出用例](artifact-csv-explanation-portable-support.ts)

导入解释复用用例使用两张读数相同的已发送 **用户导入** 卡，其中第二张复用了第一张。确认并刷新草稿后，Edge 打开选中的第二张卡，核对两份原始锁定页，再返回原问题和附件。手动发送一次后，DeepSeek 收到两份原始页和导入标记。新追问刷新后能依次打开完整来源链，在最早来源再次刷新后可沿两站逐层回到展开的新追问。用例检查全程不读取原 CSV、不重算，模型仅在这次发送时调用。

无密钥导入来源用例使用两张读数相同的已发送 **用户导入** 卡。恢复的草稿和已保存的追问均可通过 **查看这次复用的来源追问** 打开这次确切选中的卡。Edge 核对两份原始页的参与行，并验证全程不提交追问、不调用模型、不读取原 CSV 或重算。

导入来源链用例分别从草稿和已保存追问沿两次连续复用向前查看。在最早追问刷新后，Edge 经由中间追问返回确切的草稿或展开的已发送追问。草稿保留原文字、光标和锁定页。用例核对两份原始页，并检查全程不提交追问、不调用模型、不读取原 CSV 或重算。

浏览器还会在草稿中打开 **查看完整来源链** 并核对两条已保存追问，关闭列表后再打开。直接选择最早的追问时，中间对照保持收起。刷新后，仍可沿返回路径恢复原光标和同一份附件。

浏览器也从新发出的追问打开完整来源链，直达最早来源。刷新后可回到出发的已发送对照，保留另一份未发送草稿。若已从草稿进入这条已发送追问，再查看完整来源链，选中追问后会保留到原草稿的返回路径。

较早的历史页暂时无法读取时，浏览器核对预览只显示已验证的来源。用户仍能打开可用的对照。历史读取恢复后，点 **重试** 会补齐缺失的来源。来源引用的消息 ID 不匹配时，列表会标明失效的层级，已核对的对照仍可打开。

浏览器也会在这两种情况下刷新已打开的来源页，核对页面先回到最后一条可用对照。历史恢复后可重试回原位置，返回草稿时光标和附件凭据仍在。引用失效时，可用对照上会显示断开的层级。浏览器还会在重试时暂缓一份成功的历史响应，先返回草稿、打开另一条来源路径，或切换会话并打开那里的来源对照。放行响应后检查所选会话、聚焦的对照和返回路径。刷新恢复该会话的路径，期间不调用模型、不重算 CSV。

右侧栏中的测试标签页会在重试期间保留第一个会话，浏览器切走后再切回。放行较早的历史响应后，检查目标对照仍收起，焦点仍停在用户原先的位置。再次点 **重试** 会打开目标对照并恢复返回路径。刷新会重新打开同一对照和路径，期间不调用模型、不重算 CSV。

浏览器再做一次会话往返，在放行第一份历史页响应前发起新重试。两次重试共用会话的历史加载。目标所在的历史页仍暂缓时，新重试保持等待状态，焦点留在最后一条已核对的对照上。放行目标历史页后，打开原先请求的对照。刷新后能恢复该对照和返回路径，期间不调用模型、不重算 CSV。

双页回归覆盖三种结果。目标历史页暂缓时，浏览器在两个会话之间切换，右侧栏持续保留第一个会话。

- 第一个会话的最新重试仍在等待时切到第二个会话，打开它的来源对照。迟到的页面会补齐第一个会话保留的历史，焦点和返回路径留在第二个会话。
- 目标页到达前切回第一个会话。收到响应后，最后一条已核对的对照保持焦点，目标继续收起。重新点 **重试** 才会用已加载的历史打开目标。
- 在目标页仍暂缓时切回第一个会话并发起新重试。等待期间焦点留在最后一条已核对的对照，目标页到达后只有新重试会打开目标，且只打开一次。

每种情况刷新后都只恢复当前会话的对照和返回路径。导航和重试期间不调用模型、不读取原 CSV、不重算。客户端回归覆盖 2、3、9、12 次重试，分别检查共用历史响应，以及最新重试先于或晚于旧重试收到各自响应。

无密钥 Web 回放载入两条已保存的会话，使用宿主提供的历史页，每种结果完整往返两次。真实模型验收使用同一套浏览器断言，每种结果往返八次。PR CI 的常规 Web 浏览器测试用 Playwright Chromium 运行回放。本地可设置 `AGENTRANS_PLAYWRIGHT_EXECUTABLE_PATH`，用 Edge 运行同一用例。[无密钥来源重试回放](csv-source-retry-replay.e2e.ts)

## 完成状态观察

依赖状态的用例使用 Workspace、接纳、附件和模型流屏障，区分可见中间状态与已完成操作。模型选择器的持久化断言等待默认设置保存完成，不以菜单关闭作为完成信号。详情关闭等待框架过渡结束；归档验证为 seed Session 设置显式标题，并跨重载跟踪该身份。[CI 测试可靠性工作流](../../../.agents/skills/dsh-ci-test-reliability/SKILL.md#synchronize-on-state)负责这些同步规则。

[空闲提交交接](idle-submission-handoff.e2e.ts)对 Host 帧和浏览器中的消息归位的等待使用 scaffold 的 30 秒 Turn 完成预算。Vitest 负责 scaffold 清理，使 replay 消耗检查错误不会覆盖场景中失败的断言。

插件管理器和 HMR 生命周期场景中的开关为 Host 的 profile 写入与 store 随后的 inventory 读取预留 `PLUGIN_TOGGLE_SETTLE_MS`（10 秒），这两步完成后才会重新发布 `aria-checked`；链路的实测值记录在该常量的 JSDoc 中。

显式滚动使用 `support.ts` 的 `scrollIntoView`：旧元素脱离 DOM 时重新解析 locator，并在同一个浏览器任务中检查连接状态、执行原生滚动。各场景保留滚动后的可见性与几何断言。

问答输入框的缩放断言等待 CSS 滚动时间线更新，使溢出、裁剪遮罩与展开按钮的可见性一致。

[侧栏窗格关闭后的快照](shortcuts-panels.e2e.ts)在捕获前将指针移出控件，并等待悬停提示关闭。键盘焦点保持在窗格上。

[同源窗口终端用例](sidebar-terminal.e2e.ts)等待 UI 触发的 Host 关闭操作完成后，再检查进程终止。它还检查第一个窗口的进程、保存的绑定以及重载后的布局。

## 这些是 Host 面的测试

它们在根 `tsconfig.host.json` 中做类型检查，而不在 Client aggregate 中，因为它们直接读取 Host 服务：`ctx.connection`、Host 侧 `SessionStore` 与 `ctx.sessionProjectionCache`。运行时驱动浏览器并不使一个文件成为 Client 程序的一部分——两个 face 在相同的键上以不同服务合并 Cordis `Context`，因此单个程序无法同时看见两者。把这些文件挪进 Client aggregate 会让每一处 Host 服务访问都无法编译。

新增场景要在同一次改动里登记到两份工程清单：根 `tsconfig.host.json` 的 include，以及 Client aggregate `apps/web/tsconfig.json` 的 exclude。该工程包含整个 `tests` 目录，漏登记 exclude 的文件会按 Client 代码编译，`pnpm run typecheck` 的 Client compiler 关卡会一直以 Host 服务错误失败，直到它被列入。

## 不要在此 import `@agentrans/client-*`

import 一个 Client 包——无论值还是类型——都会把它的 TypeScript 工程及其引用的工程拉进 Host 构建图。生成的 Remote 声明在包编译之前就绪，但这并不使 Host 与 Client 的 Cordis `Context` 声明兼容。保留这些测试的 Host face 归属，只使用下文明确的 built-client harness 例外。

当某个场景需要 Client 持有的常量或纯函数时，改为在此处镜像一份，并紧挨着一条注释掉的 import 点明源模块。这样漂移会表现为选择器未命中或镜像值陈旧——是响亮的失败，绝不会是静默通过。`scaffold.ts` 按此规则镜像 welcome-notice 的 namespace、确认字段、版本和被断言的中文文案。

built-client harness 是例外。`assembled-boot.ts` import `AppWebEntry`、boot manifest（元数据清单）类型与 `RemoteMock`；`assembled-remote.ts` import Client test runtime 的默认响应与 `RemoteMock`。这些包是显式的工程引用，用于通过测试持有的 carrier 启动真实 shell。chat 场景仍在 `support.ts` 中镜像 `conversationContextKey`，而不 import 其 Client owner。

没有任何机制强制这条规则；靠 review 守住它。
